# 纪律法规爬虫（中纪检 + 校纪检）

从中纪委国家监委「党纪法规库」与北京理工大学纪检监察「法规制度」栏目抓取法规页面，导出 PDF 并按分类归档；按标题版本族去重后上传到 RAGFlow 学科智能体知识库；支持迁库、解析并发窗口、每日定时任务与 Web 监控界面（运行 / 测试两种模式）。

> 分步上手指南（本地运行、服务器部署）见 [Instruction.md](Instruction.md)。

## 工作原理

### 抓取

- **中纪检**（<https://www.ccdi.gov.cn/fgk/index>）：
  1. 用 Playwright 打开「全部数据」视图，按公式 **每页条数 ×（总页数 − 1）+ 末页条数** 估算可爬总数（实测 10 × 644 + 4 = 6444）。
  2. 依次点击左侧 16 个子分类导航（`getContent('law_validity_xxxx')`），进入类目页后解析条目、按 `submitForm_1(页码, cstart)` 翻页。
  3. 逐条进入详情页导出 PDF，按 `党内法规制度/党章` 这类分类路径落盘。**流式抓取**：进入类目即抓，不预先收集完整目录。
- **校纪检**（<https://jwjc.bit.edu.cn/fgzd/index.htm>）：用 requests 解析列表全部分页（总数直接取页面显示的「共 N 条」），再用 Playwright 逐条导出详情 PDF；部分条目链到外站也会一并保存。
- 两个来源**可以并行**（`crawl.parallel_sources`，各自启动独立浏览器实例），也可以顺序执行。
- 站点使用自动化指纹识别（`navigator.webdriver`）会触发滑动验证。程序默认带 `--disable-blink-features=AutomationControlled` 启动并注入反自动化脚本（`crawl.stealth`），实测无 cookie 也能正常抓取；不需要保存任何浏览器数据。

### 增量与计数

- 每条文档有一个稳定唯一键：中纪检 `ccdi:{详情页数字ID}`，校纪检 `bit:{详情页文件名}`（外链用「域名+哈希」）。
- 抓取前先查状态文件：**键已登记且记录的 PDF 文件仍存在** → 跳过，不重复下载、不计新增。
- 只有首次出现的新键才会让 `新增数` 与进度计数 +1；只重下（例如 PDF 被删）不算新增。
- 运行模式下进度计数**从已有数量开始累计**（例如已爬 972、本次新增 12 → 显示 972/984 → 984/984）；测试模式下每次只取**尚未爬取**的条目，所以每轮都会继续往后新增。

### 重启时的日期与版本索引

- 中纪检、校纪检各有独立时效标志 `maintenance_flags.ccdi` / `maintenance_flags.bit`，首次运行前为 `false`。
- 维护流程升级到 schema 4 时，会一次性清除旧版 `backfill_resume.json` 和旧补录状态，从新流程重新核对；本地 PDF 与文档登记不受影响。
- 标志为 `true` 时直接沿用已有日期和索引，不联网、不重建。
- 标志为 `false` 时，分别从中纪检、校纪检扫描 `crawler_state.json` 的文件总数和有日期文件数；两者一致则跳过联网日期补录，不一致才联网。
- 每次真正开始新的联网日期补全时，会先清空该来源的 `backfill_status` 和对应断点，再从当前年份/目录第一页重新开始。
- 每个来源按“日期补全 → 文件名日期兜底 → 版本索引建立”的顺序执行，两个来源并行；索引完成后对应标志置为 `true`。
- 日常定时爬取没有新增或变更时不改标志、不执行日期/索引维护，也不触发上传；有更新时对应标志置为 `false`，爬取结束后自动维护再上传。
- 中纪检日常维护的新条目来自按年份高级检索，只记录发布年份，不再为日期额外查询详情页或保存具体月日。

### 上传

- 爬取与上传是两个独立环节，按「先爬取、爬取结束后再上传」的顺序执行。
- 首次采集必须先完成全量爬取，再自动执行中纪检/校纪检日期补全和版本索引建立，最后才批量上传；爬取期间不会提前上传。
- 之后：上传方式选「自动」（`upload.mode: auto`，**默认值**）时，有新增或变更的爬取结束后先执行日期补全和索引建立，再自动上传。没有更新时不改变时效标志、不维护也不触发上传。
  - `upload.strategy` / `interval_days` 仍用于独立的定时上传检查点和历史待上传文件。
  - `interval`（**默认**）：每 `upload.interval_days` 天（默认 3 天）到 `schedule.upload_time` 这个检查点，把**所有未上传文件一次性传走**，不看文件保存了几天；没到期的检查点直接跳过。界面上的「下一次上传」显示的就是真正会执行的那一天。
    - 天数为 **0** 时退化成「随爬取立即上传」：每次爬取结束就把所有未上传文件推走（和首次运行一样），「下一次上传」显示为「随爬取立即上传」。
  - `age`（旧行为）：每天到上传时间点，只传**已保存满 `upload.min_age_days` 天**的文件。若当天的上传时间点已过，爬取结束后立即上传。
  - 点「立即上传」或首次运行仍然忽略一切期限，但只推送**每个标题族的最新版本**。
  - 上传使用滚动解析窗口：默认最多 `upload.max_parsing_documents`（30）个文件同时处于 `RUNNING/UNSTART/PENDING`。任一文件完成后立即上传并启动下一个；长时间未完成会持续等待，不设超时、不取消。只有服务器返回 `FAIL` 才按间隔定期重试，最多 3 次。

## 配置说明

全部配置在 `config.yaml`，也可用环境变量 `RAGFLOW_API_KEY` 覆盖 API Key。

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `output_dir` | `./data/regulations` | PDF 输出根目录；可用 `--output-dir` 覆盖 |
| `crawl.request_delay_min_seconds` / `_max_seconds` | `1.0` / `3.0` | **中纪检**每条之间的随机间隔（秒），每条在该区间内随机取值，避免固定节奏被识别 |
| `crawl.bit_request_delay_min_seconds` / `_max_seconds` | `0.5` / `1.0` | **校纪检**每条之间的随机间隔（秒）；该站点无反爬，区间可短一些 |
| `crawl.detail_page_delay_min_seconds` / `_max_seconds` | `1.0` / `2.0` | **中纪检每导出一条详情页后**再额外随机停顿（秒）；只对真正导出的条目生效，已爬过被跳过的不停 |
| `crawl.throttle_wait_ranges` | `[[10,15],[2,3],[1,2]]`（分钟） | 限流退避的**逐轮**等待区间：第 1 次等 10~15 分钟（让站点限流窗口过去），第 2 次 2~3 分钟，第 3 次 1~2 分钟；轮数超出条数时沿用最后一条。旧写法 `throttle_wait_min_seconds` / `_max_seconds`（秒）仍兼容，等价于所有轮次用同一个区间 |
| `crawl.throttle_max_rounds` | `3` | 连续限流退避次数上限（不写时等于上面区间的条数）：连续这么多次仍被限流则报错并暂停本轮；中途一旦成功计数归零（`0` = 不限次数） |
| `crawl.throttle_retry_minutes` | `30` | 连续退避用尽后，隔多少分钟自动重试（从断点续爬）；`0` = 不自动重试，等下次定时爬取 |
| `crawl.resume_max_age_hours` | `12` | 中断（Ctrl+C / 终止 / 限流）后，在该小时数内重启会从断掉的分类和页码接着爬；上一轮已完整跑完或超出该时间窗则从头全量扫描（`0` = 每次都全量扫描） |
| `crawl.playwright_headless` | `true` | 是否无头运行；遇到验证页时可设为 `false` 手动过 |
| `crawl.page_load_timeout_ms` | `120000` | 页面加载超时 |
| `crawl.human_verification_wait_seconds` | `300` | 有头模式下等待人工完成验证的秒数 |
| `crawl.skipped_category_retry_minutes` | `30` | 中纪检子分类被跳过（错误页/取不到列表/翻页中断）后，间隔多少分钟自动**只重爬这些分类**；`0` = 不自动重试（下次完整爬取时仍会再试） |
| `crawl.skipped_category_retry_max_rounds` | `3` | 同一批跳过分类最多自动重试几轮，`0` = 不限轮数 |
| `crawl.parallel_sources` | `true` | 中纪检与校纪检是否并行爬取 |
| `crawl.pdf_scale_ccdi` | `1.0` | 中纪检 PDF 渲染缩放（0.1~2.0） |
| `crawl.pdf_scale_bit` | `0.7` | 校纪检 PDF 渲染缩放，避免内容超出右边界（可按需调整） |
| `crawl.browser_channel` | `chrome` | 浏览器内核，留空=自带 Chromium；不可用时自动回退 |
| `crawl.stealth` | `true` | 隐藏自动化特征（关键参数） |
| `crawl.rotate_user_agent` | `true` | User-Agent 池随机轮换：每进入一个分类、每导出一条详情页都换一个 UA（内置 Chrome/Edge/Firefox 的 Windows UA） |
| `crawl.user_agents` | 空 | 自定义 UA 列表；留空（或不写）用内置池；要关闭轮换就把 `rotate_user_agent` 设为 `false` |

> 间隔支持三种写法：`[1, 3]`（区间）、`"1-3"`（字符串区间）、`2`（固定值）。旧配置里的单个 `crawl.request_delay_seconds` 仍兼容：没有新的 min/max 时按固定间隔使用。
| `schedule.crawl_time` | `"02:00"` | 每日爬取时间点；留空=不启用该定时任务 |
| `schedule.upload_time` | `"03:30"` | 每日上传时间点；留空=不启用 |
| `schedule.timezone` | `Asia/Shanghai` | 定时任务时区，留空用服务器本地时区 |
| `upload.mode` | `auto` | 上传方式：`auto`=爬取结束后按策略自动上传；`manual`=只在点「立即上传」时上传。界面上的「上传方式」开关会写回这里 |
| `upload.strategy` | `interval` | 运行模式上传策略：`interval`=每 N 天把所有未上传文件一次性传走（不看年龄）；`age`=每天只传保存满 `min_age_days` 的文件 |
| `upload.interval_days` | `3` | `interval` 策略的周期（天）；`0` = 每次爬取结束立即上传全部未上传的最新版本 |
| `upload.min_age_days` | `3` | 仅 `age` 策略使用：定时上传前至少保留的天数 |
| `upload.max_age_days` | `4` | 预留参数，当前不用于限制上传截止 |
| `upload.max_parsing_documents` | `30` | 滚动窗口内最多同时处于解析状态的文件数 |
| `upload.parse_poll_seconds` | `10` | 解析状态轮询间隔 |
| `upload.parse_retry_rounds` | `3` | 服务器返回 `FAIL` 后最多重新触发的次数，上限固定为 3 |
| `upload.parse_retry_interval_minutes` | `10` | `FAIL` 文件的定期重试间隔 |
| `ragflow.base_url` | — | RAGFlow 地址（`.../api/v1`） |
| `ragflow.api_key` | — | RAGFlow API Key，建议用环境变量注入 |
| `ragflow.dataset_name_ccdi` / `dataset_name_bit` | `中纪检` / `校纪检` | 两个知识库名称 |
| `ragflow.chunk_method` / `chunk_token_num` | `laws` / `512` | 分块方式与大小 |
| `ragflow.dataset_id_ccdi` / `dataset_id_bit` | 空 | 库已存在时可填 ID 跳过自动创建 |
| `monitor.host` / `monitor.port` | `0.0.0.0` / `8765` | 监控界面监听地址与端口 |
| `logging.level` | `INFO` | 日志级别；只关心告警和错误就填 `WARNING` |
| `logging.http_access` | `false` | 是否记录每个 HTTP 请求；UI 每秒轮询，默认关闭避免刷屏 |
| `logging.file` | `""` | 留空=只输出控制台（配合 `nohup >> logs/app.log` 或系统 logrotate）；填 `logs/app.log` 则由程序写文件并自动轮转（此时启动命令重定向应改成 `>/dev/null`） |
| `logging.max_bytes` / `backup_count` | `10485760` / `5` | 内置轮转的单文件上限（10MB）与保留份数 |
| `logging.run_log.enabled` | `true` | 每次爬取单独写一个日志文件 `logs/runs/<开始>至<结束>.log` |
| `logging.run_log.dir` | `logs/runs` | 每日运行日志目录 |
| `logging.run_log.keep_days` | `7` | 没有 ERROR 的日志保留天数；有 ERROR 的一律保留 |

**每日运行日志**：每次爬取（每日定时 / 首次全量 / UI 点开始 / `--crawl-now` / 自动重试）都会单独写 `logs/runs/20261019-10:33:11至20261019-10:50:11.log`（Windows 本地运行时冒号非法，自动用 `20261019-10-33-11至20261019-10-50-11.log`）。下一次爬取开始前会检查**昨天**这一天的日志：有 `[ERROR]`（或未捕获异常的 `Traceback`）就在界面顶部弹红色横幅并列出文件名，这些文件永久保留；没有错误则按 `keep_days` 过期删除。开启它之后，nohup 重定向的 `logs/app.log` 只保留 WARNING/ERROR，不会再被 INFO 刷满。

**关闭浏览器不影响运行**：8765 只是同进程里的一个独立 Web 线程，爬取/上传/定时任务不受浏览器是否打开影响。Web 服务异常退出会自动在 30 秒后重启；`/api/status` 等接口异常也只返回一次 JSON 500，不会把 UI 线程带崩。

> 在监控界面里修改的设置（每日时间点、校纪检缩放、RAGFlow 地址与库名等）会写回 `config.yaml`。

## 监控界面

浏览器打开 `http://<主机>:8765`（默认监听 `0.0.0.0`）。

**总控制（页面最上方）**

- **开始 / 暂停 / 继续**：圆形图标按钮。空闲显示 ▶，按当前模式启动任务；运行中变橙色 ⏸，点击挂起（爬取/上传在条目边界停住）；挂起后再点 ▶ 从原处继续。
- **终止**：红色圆形 ■，终止所有任务（含爬取结束后的自动上传）。
- **立即上传**：手动推送所有未上传文件（上传方式为「自动」时隐藏）。
- **保存位置**：直接修改输出目录，点「应用保存位置」生效（需无任务运行）。
- **爬取方式**：顺序 / 并行切换。
- **上传方式**：手动 / 自动切换（原来在模式卡片里的「爬取结束后上传」已移到这里，两个模式共用）。
- **上传进度条**：上传开始后显示，按“已推送到 RAGFlow 的数量”更新；默认最多 30 个文件同时处于解析状态，任一文件完成后立即补传下一个。长时间解析会持续等待，服务器返回 `FAIL` 才按配置间隔重试，最多 3 次。

**任务控制**

- **模式**：标签页切换「运行模式 / 测试模式」。
  - 运行模式：全量爬取全部来源；可配置**每天的**「每日爬取时间 / 每日上传时间」（留空=不启用），下方以标签显示「下一次爬取 / 下一次上传」；卡片底部只读列出当前关键配置（不含 API Key）。
  - 测试模式：可选来源、限制每个来源的条数（「全量测试」则不限条数、总数按运行模式口径）、配置校纪检 PDF 缩放。**定时方式二选一（同时管爬取与上传）**：
    - `按间隔`：每隔 N 分钟/小时触发一次爬取、一次上传（各自可设，0=关闭）；
    - `按每日时间点`：直接在这里填「每日爬取时间 / 每日上传时间」（留空=不启用），与运行模式共用同一组时间配置；到点时**爬取使用测试模式的来源与条数**，**上传推送全部未上传的最新版本**（不受 3 天保留期限制）。
    下方显示「下一次爬取 / 下一次上传」；爬取时两个来源并行执行。选「按每日时间点」后间隔任务整体停用。
- **提示横幅**：中纪检触发人机验证、或连续退避 3 次后仍被站点限流时，页面顶部会弹红色横幅（可手动关闭）；验证通过 / 下一轮爬取正常结束后自动消失。
- **首次运行标注**：检测到输出目录里还没有已登记文档时，页面顶部显示黄色的「首次运行」提示；在下一次定时任务执行时自动取消。
- **首次运行顺序**：先完成全量爬取，再补日期、建立索引，最后统一上传；爬取和维护期间不会提前上传。

**进度卡片**：「中纪检」「校纪检」「今日 / 总量」三张卡片排版一致——库名居中放大 + 状态标签 + `N / M 条` + 进度条 + 当前目标 + 「上次爬取 / 上次上传」时间标签；运行中右上角显示圆形终止按钮。测试模式若「实际可爬条数」少于设定条数，会在卡片上用黄色提示标注。

中纪检的当前目标行是 `[扫描 N/总数 · 已爬 K] 名称`：**N 是本轮扫描到第几条**（每处理一条 +1，与后面的名称一一对应，不会出现"序号不动而名称在变"），**K 是累计已爬数量**。中断重启后续爬时 N 会接着上次继续，不会归零。

中纪检卡片在多出「当前分类：党内法规制度/条例」一行；遇到站点限流时会显示「站点限流（请求过于频繁），暂停 X 分钟后重试（第 N/3 次，预计 2026-10-17 00:41:41）…」，明确写出下一次尝试的具体时间（日期 + 时分秒，与其它时间标签同一格式）。
卡片上的活动行是「本轮已扫描 N 条 · 打开详情页 M 个 · 新增 K 个」：**N 是列表条目数（已爬过的只做本地比对，不产生任何请求）**，**M 才是真正打到站点的页面请求数**（每导出一个 PDF 就要完整加载一次详情页）。所以"扫了 241 条、新增 0 个"说明这一轮主要在跳过已爬条目，对站点几乎没有压力。
卡片上还有一行「`[200] https://…`」：**当前正在访问的网址与 HTTP 状态码**（每读完一页、每导出一条就刷新）。状态码 2xx 绿色、3xx 蓝色、4xx/5xx 红色；网址太长时只显示末尾 52 个字符，鼠标悬停可看完整地址。正在加载还没拿到响应时，标签显示「请求中」，网址已经是即将访问的目标地址。想判断是不是真限流，看这一行就够了：`error.html` 才是限流页，`weihu.ccdi.gov.cn` 是维护页，`law_pagenumb` 只在**启动时估算库总量**时出现（有缓存后一般不会再访问）。

**中纪检 · 子分类进度**（三张卡片下方，整行、可折叠）：逐行列出 16 个子分类的「已爬 / 共多少条」（带 `~` 的是按「每页条数 × 总页数」估的，**从第 1 页完整扫完一遍后**才换成精确值）、状态标签（待爬 / 爬取中 / 完成 / 部分完成 / 跳过·原因 / 已中断），当前分类整行高亮并在「已爬 / 共」下显示小进度条。被跳过的分类会额外标注「已安排重试 · 2026-10-17 10:35:21」或「未安排重试」。点标题行可折叠/展开。
   - 「完成」是数据驱动的：重启后分类状态会先重置为待爬，但**已登记条数达到（精确）总数时会直接显示「完成」**，不会因为重启而变回待爬。
   - 「**部分完成**」表示该分类被标记完成、但已登记条数明显少于精确总数（例如 10/53）——说明那一轮没真正爬全（页面解析失败或被中途打断）。看到这个标签，把 `crawl.resume_max_age_hours` 设为 `0` 跑一轮全量即可补齐。
   - 续爬（从中间某页接着跑）时只补后半段，**不会**把这半段的条数当成分类总数（之前会出现「60 条的分类爬 10 条后变成 10/10」）。

卡片上还有一行**本轮活动量**：「本轮已扫描 N 条 · 新增 M 个」。卡片中间的大数字（`累计已爬 / 库总量`）只在「新增」或「补写丢失的 PDF」时前进；扫描大量已爬过的分类时它不动是正常的，看扫描序号和这一行即可确认程序仍在工作。

中纪检卡片还会用一排**小标签**显示「上次区间」：

`[上次区间]` `[正爬最大有效 7200]` `[倒爬最小有效 68560]` `[倒爬最大有效 71065]` `[最大有效编号 71065]`

对应 `id_walk.ccdi` 里的 `forward_last_valid` / `backward_last_valid` / `backward_max_valid` / `last_valid_id`。日常维护时，新编号落在 `[正爬最大有效, 倒爬最小有效]` 空档或 `[倒爬最大有效, +∞)` 就按新增处理，并更新对应边界。

任务结束时卡片会写明本轮结果，`空闲` 只表示当前没在跑：正常跑完是「完成，本次新增 128 个（分类 16/16 · 扫描 6300 条 · 用时 125 分钟）」，被终止是「已终止，停在 党内法规制度/办法，本次新增 …」，持续限流是「站点持续限流，本轮提前结束 …」。中纪检的分类爬取顺序是「党章 → 准则 → … → 国际公约」，最后一条落在**国际公约**通常意味着整轮正常跑完。

「今日 / 总量」卡片标题下方有一个状态小标签：还没有已登记文档时显示「**首次执行**」，下一次定时任务执行后变为「**日常执行**」；若当前进程没启动定时任务（`--no-schedule --no-ui`），会额外显示「定时任务未启用」。

所有时间标签统一格式为 `YYYY-MM-DD HH:MM:SS`。

**学科智能体信息卡片**：左侧「中纪检」「校纪检」两张知识库卡片上下排列、内容居中靠上，使用浅蓝底色，合并高度与右侧「上传与解析」卡片一致；库 ID 居中显示。上传卡片内只保留「中纪检」「校纪检」两栏；每栏用「日期补全」「索引建立」小标签和分割线分成两个区域。中纪检日期详情使用可折叠年份表，点击年份行可展开页码子表。解析超时/失败待重试的 RAGFlow 文档 ID，用可展开/收起的框放在对应的「中纪检」或「校纪检」库卡片中。下方两张爬取进度卡也使用区分来源的浅色底色；日期补录限流警告只显示在中纪检日期补全区。

中纪检年份明细采用与「中纪检 · 子分类进度」一致的折叠表格：每行是一个年份，显示已扫描/总条数、当前页/总页数、完成/补录中/部分完成/异常/无需补录状态、进度条及未完成页说明；当前年份高亮。日期补录翻页前和页面成功加载后都使用 `crawl.request_delay_min_seconds/max_seconds` 的随机等待。

「上传与解析」最上方的大计数始终为中纪检与校纪检两个来源的“已有日期文件数之和 / 文件总数之和”，不是单独的中纪检计数，也不再用扫描页数替代实际日期数量。

高级检索结果页优先读取 `检索数量：N` 作为该年权威总数。每个年份要么本地年份文件数一致而跳过，要么页面完整爬取成功；所有年份都成功处理后，再对仍无日期的文件做文件名兜底。即使兜底后日期数仍少于文件总数，也继续建立索引，不以本地文件总数作为完成门槛。失败年份最多重试 3 次，仍不完整才标异常。重启时优先恢复“年份 + 下一页”断点。

**历史记录**：分页（每页 10 / 20 / 50 / 100 条）+ **页码按钮**；排序、来源、分类、上传状态与原来一致。存在多个版本的历史记录会带「N 个版本」标签。

**多版本文档**独立成卡片，可整体展开/收起；支持标题/链接后缀/位置搜索、全部/中纪检/校纪检分类按钮、每页 5/10/20/50 条、上一页/下一页、页码跳转。每个标题族可继续展开版本明细，编号列已加宽并允许换行，避免与标题重叠。

## 输出目录与状态文件

> 想随时看两个来源各有多少个 PDF：`python count_files.py`（`--detail` 按子分类细分，`--dir` 指定目录；只读，不影响运行）。

```
{output_dir}/
  crawler_state.json          # 进度、文档登记、上传统计、告警
  backfill_resume.json        # 日期补录断点（年份、页、年份统计、目录页）
  category_totals.json        # 各子分类条数基线（日常维护按它判断哪些子分类有新增）
  .crawler.pid                # 当前实例的 PID（防重复启动；退出时自动删除）
  中纪检/
    党内法规制度/
      条例/
        中国共产党纪律处分条例.pdf
    国家法律法规/法律/…
  校纪检/
    中国共产党章程.pdf
```

`crawler_state.json` 主要内容：

- `documents`：当前来源条目的唯一键、标题、发布日期、本地 PDF 路径、当前版本 ID、上传时间、上传库 ID 与 RAGFlow 文档 ID。
- `version_records` / `version_indices`：每个本地文件的版本记录，以及**分别建立**的 `version_indices.ccdi` / `version_indices.bit`；每个来源独立记录版本族、链接后缀、标题、位置、日期和最新版本。`version_index` 仅保留两者的合并视图供历史列表读取。
- `version_index_meta`：中纪检、校纪检各自的索引建立时间、已录日期数、缺失日期数、错误和最近一次索引说明；上传门禁由 `maintenance_flags` 控制。
- `maintenance_flags`：中纪检、校纪检各自的日期与索引时效标志；`true` 时直接复用已有数据，新增或变更后置为 `false`，维护完成后恢复为 `true`。
- `backfill_status`：中纪检、校纪检各自的日期补录状态，以及版本索引建立状态、进度、当前年份/页码和最近更新时间。
- `backfill_resume.json`：轻量断点文件。中纪检保存当前年份、已核对页、下一页、该年总页数/条数和本年已补数量；校纪检保存目录页进度。中断重启后从下一页继续。
- `parse_queue`：正在解析、`FAIL` 待重试以及重试耗尽的 RAGFlow 文档 ID、下一次重试时间和状态说明；长时间解析不会因超时进入该队列。
- `progress`：`ccdi` / `bit` / `upload` 的状态、进度、当前消息、提示（note）。
- `last_crawl_time` / `last_upload_time`：各自来源的上次时间。
- `daily_new_count`：按日期的每日新增数。
- `alerts`：需要在界面提示的信息。

> 想整体重来（全部重新算新增并重传），删掉 `crawler_state.json` 即可；想保留记录只重下某个文件，删掉对应 PDF 即可。

## 注意事项

1. **中纪检人机验证**：无头模式下访问类目页可能返回滑动拼图验证页，根因是自动化标记（`navigator.webdriver`），与 cookie 无关。程序已默认规避（`crawl.stealth`），实测在全新、无任何 cookie 的环境下可直接抓取。若个别环境仍被拦截，把 `crawl.playwright_headless` 设为 `false` 再跑，程序会等待人工完成验证（最多 `crawl.human_verification_wait_seconds` 秒）。
2. **首次全量爬取**：以状态文件里的「首次执行」标记判断（没有任何已登记文档时自动置位；`id_walk` 方式下要等中纪检编号扫到上限、校纪检也跑完才清除）。首次完成后自动执行日期补全、索引建立和上传，页面同时显示「首次运行」标注。想隔离试跑数据用新的 `--output-dir`，想手动控制在 UI 里触发就加 `--no-auto-start`。
   - **首次运行标记会持久化**：一旦开始就写进状态文件，只有**两个来源都完整跑完**才清除。首次运行中途被中断，重启后仍按"首次运行"继续，不会掉到日常模式。
   - 首次运行续跑时，**已经标记「完成」的子分类直接跳过**（连列表都不重新扫），只补没跑完的部分。
   - 首次运行会把每个子分类的条数按「(页数-1)×每页条数 + 末页条数」算好，写进 `output_dir/category_totals.json`，作为日常维护的对比基线。
   - **首次爬取途中撞上「每日爬取时间」**：爬取跳过（不排队、不补跑，下一次是第二天的同一时间）；「首次执行」标记保留到中纪检编号扫到上限且校纪检完整跑完。
   - **爬取或维护途中撞上「每日上传时间」**：本次定时上传跳过，避免在日期/索引未完成时提前上传；维护完成后由自动流水线统一上传。
   - 定时任务在进程启动时就注册；首次长爬取期间到点的上传会跳过，等待“爬取 → 日期补全 → 索引建立”全部完成后再上传。
3. **异常页自动重试（非限流）**：中纪检某个分类若出现「没有左侧导航」「没取到列表」「页面打不开」，程序会**等待 2 秒 → 重新进入法规库首页 → 再跳转该分类**，最多尝试 3 次；单次等待列表上限 15 秒。三次都失败才跳过该分类（只影响这一个分类，后面的照常爬），日志会打印当时的 URL 与页面标题。若是识别到限流页（`/error/error.html`），则改走下面第 4 条的退避策略。
   - **单个页码取不到条目**（翻页后是过渡页/还在加载，日志「第 N 页共 0 条」）时，不会直接放弃：会**直接访问该类目页（`/fgk/<分类码>`）→ 重新 `submitForm_1(N)` 翻到第 N 页**再解析，最多 3 次；仍失败才把该分类按「翻页中断」跳过并登记 30 分钟后重试。跳过时若本轮还在跑，卡片上会显示「爬取结束后安排重试」，而不是「未安排重试」。
     - 重试日志会带**当前页面 URL、要回去的类目页 URL、失败原因**：`页面内容读取失败（可能仍在跳转）` / `读到 32505 字节但没有解析出条目` / `翻到第 N 页后落到站点限流页`。
     - 如果翻页的表单 POST 被限流（落到 `/error/`），会按限流退避处理（而不是当成解析失败）；翻页前若发现页面不在类目列表（被带到详情页），会先回类目页再翻。
     - 站点还可能把请求拦到 `https://weihu.ccdi.gov.cn/index.html`（正文「网站正在维护中，请稍后访问」，页面约 4KB、没有列表）——实测翻页时偶发，**紧接着访问别的分类又是正常的**，所以它按"页面级拦截"处理：短等 2 秒后回到类目页重翻同一页（不做 10~15 分钟的长退避），日志写「站点维护页（网站正在维护中）」。只有 `/error/error.html`（正文「您的请求过于频繁」）才走逐轮退避。
       - 处理顺序固定为：**先等 3 秒**（回该子分类首页 → 重新翻到第 N 页）→ 仍是维护页就**等 6~7 分钟**（实测站点拦截约 6 分钟解除）→ 回到目录页再试一次 → 仍失败才按「翻页中断」跳过该分类（交给 30 分钟后的重试，从断掉的那一页继续）。等待期间不再对该异常页重复提交请求。**维护页不触发「站点限流」的长等待**——卡片文案是「遇到站点维护/拦截页，暂停 X 分钟后重试第 N 页（预计 2026-10-17 14:05:12）…」；只有 `/error/error.html`（正文「请求过于频繁」）才走逐轮退避，两者在卡片和日志里分得很清楚。
     - **翻页中断的分类被重试时，直接从断掉的那一页开始**（日志「从第 N 页继续：…（跳过前面的页面，不再重复扫描）」），不再从第 1 页重扫——已爬过的条目本来也会被跳过，这样能少发很多请求、也少一次被拦的机会。
4. **站点限流（「您的请求过于频繁」）**：中纪检的 `/error/error.html` 就是限流页，实测大约每 20~30 条会出现一次。程序的处理是**原地退避 + 立刻重试**：按 `crawl.throttle_wait_ranges` 逐轮随机暂停（默认**第 1 次 10~15 分钟、第 2 次 2~3 分钟、第 3 次 1~2 分钟**）→ 等到点后**马上重试**当前这条/这个分类，最多连续 `crawl.throttle_max_rounds` 次（默认 3）。第一次等久一点让站点限流窗口过去，之后多半只是瞬时抖动，短等即可。**退避后的重试不占用普通尝试次数**，所以"等 3 次"确实等于"退避后重试 3 次"。暂停期间进度卡片显示剩余说明与预计重试时间，暂停/终止按钮照常生效（暂停不计入等待时长，终止会立刻结束等待）。
   - 只要中途成功一次（取到列表或导出成功），连续计数**立刻归零**——所以「每 20~30 条限流一次」时，每次限流都能重新拥有完整的 3 次退避机会，不会因为累计而提前放弃。
   - **中断后重启不会重新随机**：退避的「到点重试时间」和轮次会写进状态文件；等待途中被终止/重启时，只要还没到点，就**只补剩下的时间**（卡片提示「继续上次未完成的限流等待：还剩 X 分钟」），不会重新抽一个 10~15 分钟；如果重启时已经过点，则按**下一轮**的短区间继续（例如第 2 次 2~3 分钟），不会又从第 1 轮等起。只有三轮都用尽（报错结束本轮）时才会清掉记录，让下一次/定时重试重新拥有完整预算。
   - 连续 3 次退避后仍被限流（说明站点在较长一段时间内限流当前 IP）：**本轮结束，并在 `crawl.throttle_retry_minutes`（默认 30 分钟）后自动重试**——日志打 ERROR、界面顶部弹红色横幅（写明具体重试时间），中纪检卡片上显示「限流自动重试：YYYY-MM-DD HH:MM:SS」；到点后从断点续爬，不需要等到第二天的定时任务。重试仍被限流就再等 30 分钟，直到成功；点「终止」会取消待执行的重试。设成 `0` 则只结束本轮、等下一次定时爬取。横幅在下一轮爬取正常结束后自动消失。
   - 详情页被限流时导出的 PDF 会是提示页，程序会**删除该 PDF 且不登记**，因此不会把垃圾文件推到知识库，也不会被误判为「已爬过」。
   - 校纪检无可见反爬，不做限流等待，只按上面的随机间隔慢慢抓。
5. **跳过分类的标识与定时重试**：分类被跳过时**不会中断本次爬取**（网络类错误如 `net::ERR_CONNECTION_RESET` 只记日志）；被跳过的分类会**立刻**写进状态文件（哪怕下一秒被 Ctrl+C 也不丢），并在「中纪检」进度卡片里列出分类名与原因（站点限流/错误页 / 未取到列表 / 页面打开失败 / 翻页中断）。爬取结束后按 `crawl.skipped_category_retry_minutes`（默认 30 分钟）安排一次**只重爬这些分类**的任务（已爬过的自动跳过），卡片上显示重试时间；重试成功后该分类自动从清单移除、任务取消。重试达到 `skipped_category_retry_max_rounds` 轮（默认 3）仍失败就停止自动重试，等下一次完整爬取再试（每轮完整爬取都会把重试轮数清零）。点「终止」会同时取消待执行的重试；重启程序时若清单里还有分类，会自动重新安排重试。某分类翻页中断时视为未完成，下次会从该分类第 1 页继续（已登记的不会重复）。
6. **进度上的两个数字（`category` 类目方式；默认的 `id_walk` 见第 19 条）**：卡片中间的大数字是 `累计已爬 / 库总量（估算）`，只在「新增文件」或「补写丢失的 PDF」时前进；标题行是 `[扫描 N/总数 · 已爬 K] 名称`，N 是**本轮扫描序号**（按 `doc_id` 去重，重试/重读同一页不会重复累加；每次启动从 1 重新数），K 是累计已爬数。增量爬取会顺序扫描所有分类并跳过已爬过的条目，此时大数字短暂不动属正常，看扫描序号 N 就知道走到哪了。
7. **中断续爬**：被 Ctrl+C / 终止 / 限流打断后，只要还在 `crawl.resume_max_age_hours`（默认 12 小时）内、且用的是同一个输出目录，重启后会**从断掉的分类和页码接着爬**（卡片提示「从中断处继续：党内法规制度/准则 第 1 页…」）。上一轮已完整跑完、或超出时间窗，则从头全量扫描——这样才不会漏掉前面新发布的文件。想每次都全量扫描就把它设为 `0`。
   - 续爬时，**断点之前被跳过（翻页中断/限流）的分类会先补一遍**，再从中断处继续：日志会打「续爬前先补上之前被跳过的 N 个分类：…」，卡片顺序也先出现这些分类。否则续爬会直接跳到断点，把它们漏掉。
   - 启动日志会明确说明本轮是续爬还是全量：`检测到上次中断的位置，从 law_validity_0103 第 1 页接着爬` / `resume_max_age_hours=0：本轮从第一个分类开始全量扫描` / `没有续爬记录…` / `上一轮已完整跑完…` / `续爬记录已过期（记录时间 …）…`。看到「从第一个分类开始」时，对着这行就能知道是配置关掉了续爬、还是上次已经跑完。
8. **浏览器连接断开自愈**：中纪检抓取中若 Playwright 连接断开（`Target page, context or browser has been closed`），程序会重启浏览器并从**当前编号**重试——导航时断开会重开这一页，导出 PDF 时断开会删掉半截文件再重导。单轮最多重启 `5` 次（`BROWSER_RELAUNCH_LIMIT`），仍失败才结束本轮并保留已抓文件、断点位置。类目翻页方式同样会在断开后重启浏览器继续。
9. **文件命名**：一律取**导航页链接文字**（href 后面的名称），不再进详情页取 `<title>`；被省略号截断的也原样保留。文件名前面加**站点顺序编号**，方便和网页列表逐条对照：
   - 中纪检：`子分类[序号] 标题.pdf`；序号 = 该条目在**子分类列表里的位置**，按 `子分类` 分别从 1 开始。
   - 校纪检：`[序号] 标题.pdf`；序号 = 该条目在整个 `法规制度` 列表里的顺序。
   - Windows 不允许的字符改成全角形式（`:`→`：`、`?`→`？`、`/`→`／`），英文双引号按开合换成中文引号（`"带病提拔"` → `“带病提拔”`），换行压缩成空格——其余保持原样。
   - **已存在的文件不会改名**；新下载文件不再追加 `_YYYY` / `_YYYYMMDD` 日期后缀。重名时使用现有唯一文件名机制追加 `_2`、`_3`。UI 的「历史记录」只显示标题本身，不带前缀。
10. **校纪检翻页**：按「共 N 条 / 每页 M 条」生成 `index.htm`、`index1.htm`…全部页；部分条目链到外站也会保存到 `校纪检/`。
11. **智能体状态统计**：分页拉取时以「翻到空页为止」为终止条件，兼容 `data` 为数组或 `{docs:[...], total:N}`；列表未带解析状态时并发查单文档详情，`run` 缺失按 `progress` 推断。总数优先用知识库的 `document_count`，每次查询会在日志打印声明总数与实际统计数。
12. **安全**：不要把含真实 API Key 的 `config.yaml` 提交到公开仓库；生产环境用环境变量 `RAGFLOW_API_KEY` 注入。
13. **暂停 / 终止粒度**：暂停与终止都在条目/批次边界生效，正在下载或推送的那一条会先结束。
14. **跨平台**：项目内的 `.playwright-browsers/` 只在 Windows 下生效（用于固定浏览器路径），Linux/macOS 一律使用 Playwright 默认缓存。因此从 Windows 迁移到 Linux 时不需要、也不应该拷贝该目录。部署细节见 [Instruction.md](Instruction.md)。
15. **User-Agent 池**：`crawl.rotate_user_agent: true` 时，每进入一个子分类、每导出一条详情页都会从内置池（Chrome/Edge/Firefox 的 Windows UA）随机取一个，用 `page.set_extra_http_headers` 覆盖请求头——实测请求头确实随之变化，抓取不受影响。想固定 UA 就设 `false`，想用自己的就在 `crawl.user_agents` 里列出来。
16. **IP 池为什么没加**：实测 [ProxyClean](https://github.com/HankNovic/ProxyClean) 公开的 100 个 SOCKS5 代理：抽测 40 个里有 13 个能建立到 `www.ccdi.gov.cn:443` 的 CONNECT，但对这 13 个发起真实 HTTPS 请求时**没有一个**能拿到页面（多数是 TLS 证书校验失败，说明流量被替换）。政府站点走这类来源不明的免费代理还有内容被篡改的风险，因此**没有接入 IP 轮换**。若以后有稳定的自有/付费代理，可以在现有 `PlaywrightPdfExporter` 上增加 `proxy` 参数接入（目前未实现）。
17. **别重复启动**：同一个输出目录同时跑两个 `main.py`，后启动的那个会因为 8765 被占用而起不了 UI（现在会打 ERROR 说明），浏览器里看到的还是旧进程——旧进程已死的话页面就一直停在旧数据。启动日志会打 `进程启动：PID … · 输出目录 … · 监控 UI http://…`，出现两个不同 PID 就是重复了；输出目录下的 `.crawler.pid` 也会在启动时提示「另一个实例还在运行」。另外，进程被强杀后状态文件里可能留着 `running`，新版本启动时会自动改回「空闲（上次运行被中断）」。
18. **日常增量怎么判断有没有更新**：
    - **中纪检**（`id_walk`），按顺序做三步：
      1. **算总数**：访问「全部数据」首页（`https://www.ccdi.gov.cn/fgk/index`），用「(总页数-1)×每页条数 + 末页条数」算出总数，和上次保存的 `total_estimate.ccdi` 比。**没增加就直接结束**（0 新增），不抓详情。
      2. **按年份高级检索**：总数增加了 → 打开 `https://www.ccdi.gov.cn/fgk/law_advancedsearch`，把「发布日期」选成**当前年份**、提交搜索，然后按结果页顺序往下爬，遇到已爬过的编号就停。
      3. **兜底**：如果高级检索被滑动验证挡住 / 翻页失败 → 先退回「全部数据」目录页扫描（遇到已爬过的编号就停）；再不行就按编号递增，从「最大有效编号 + 1」往后探测 `crawl.id_walk_daily_span`（默认 400）个编号；目录页翻页异常时，用见到的最小编号往前补到最大有效编号。
      - 编号递增一直扫到停止值都没有新增时，**最大有效编号保持不变**（`id_walk.ccdi.last_valid_id`），第二天继续核对同一段，避免漏掉后来才发布、编号又不大的文件。
      - 三个边界编号会在卡片上以标签显示：`正爬最大有效`、`倒爬最小有效`、`倒爬最大有效`。日常新增的编号如果落在 `[正爬最大有效, 倒爬最小有效]` 空档或 `[倒爬最大有效, +∞)`，就按新增处理并更新对应的边界。
    - **校纪检**：读取目录页「共 N 条」后仍会逐页核对每条标题和 `.gpArticleDate` 日期。总数相同但标题或日期变化也按新增爬取处理；全部签名一致才跳过详情页。
19. **中纪检改为「按详情页编号」抓取**（`crawl.crawl_mode: id_walk`，默认）：站点所有法规页都是 `https://www.ccdi.gov.cn/fgk/law_display/<N>`（`/0004` 与 `/4` 等价），编号从 1 到约 **71069**，中间大量编号无效。
    - 有效页从详情页里解析：`分类：党内法规制度-->规范性文件` 给出子分类，`<h2 class="tit">` 给出标题；无效编号页面只有「输入有误请…返回」，直接跳过。
    - 文件名仍是 `子分类[序号] 标题.pdf`（序号 = 该子分类已登记条数 + 1），放进 `中纪检/主分类/子分类/`。
    - **分类缺失的兜底**：详情页有效但只有一级分类（如 `分类：党内法规制度`）→ 放进 `中纪检/党内法规制度/其他/`，命名 `其他[序号] 标题.pdf`；连一级分类都没有 → 放进 `中纪检/其他/`，命名 `[序号] 标题.pdf`（和校纪检一致）。
    - **首次运行**从 1 号扫到 `crawl.id_walk_max`（默认 71069）；**日常维护**先比总数，增加了就按「今年」高级检索结果爬，检索不可用则退回目录页 / 编号递增。
    - **断点续跑**：编号位置保存在状态文件 `id_walk.ccdi`（`last_id` + `last_url`），重启后先核对断点这一号**是否真的完成**（状态里有记录、PDF 文件还在）——完成就从 `last_id + 1` 继续；没完成就只重试这一号，再往下走。不会从 1 号重扫。`scanned_max` 记录「1~N 号都已核对过」，重启时这些编号直接跳过、**不发请求**；只有上次导出失败（`failed_ids`）的编号会再试一次。
    - **双向扫描**（`crawl.id_walk_turn_back_at: 7200`）：正向扫到 7200 号后不再往前，改为从 `crawl.id_walk_max`（71069）**倒着**扫 71068、71067…，直到累计文件数达到库总量（6444）或扫回 7201。两侧各自记录**最后一个有效编号**：状态里是 `id_walk.ccdi.forward_last_valid` 和 `id_walk.ccdi.backward_last_valid`，结束时日志和卡片也会写「正向最后一个有效编号 X，倒爬最后一个有效编号 Y」。倒爬阶段的状态另存 `back_last_id` / `phase=backward`，中途重启会从 `back_last_id - 1` 继续；整段跑完后 `turn_back_done` 置位，之后回到正常的每日增量（从 71069 往后探测）。设成 `0` 可关闭，恢复成一路正向扫到上限。
    - **首次运行中途改配置也能接上**：状态里记着上次实际用的 `turn_back_at_used` / `max_id_used`。重启时如果发现 `id_walk_turn_back_at` 或 `id_walk_max` 变大了，会先补扫新增出来的区间（例如正向 6405→7200 就补 6406~7200；上限 71069→72000 就补 72000~71070），**然后再回到原来的倒爬位置继续**。补扫段不移动主游标；任何时候累计达到 6444 条就立即停止，并把首次运行标记完成。
    - **文件名有 255 字节上限**：Linux 单个文件名最多 255 字节，中文一个字 3 字节，超长标题过去会直接抛 `OSError: File name too long` 把整轮爬取打断。现在按 UTF-8 字节截断（整名 ≤ 200 字节，留出 `_2` 之类的后缀余量），文件名的前缀 `子分类[序号]` 保留；**完整标题仍然存在状态文件里**，历史记录卡片显示的是全名。
    - 已登记且 PDF 还在的编号**不发请求**。类目方式登记的编号是站点原样（`ccdi:0004`），编号枚举用 `ccdi:4`，两者会归一化比对，所以换到 id_walk 后不会把已爬过的 6000 多条重新下一遍。
    - 进度卡片中间是「已爬 / 6444」（6444 来自「全部数据」页的页码×每页条数）。这个总数会**缓存 24 小时**；缓存过期时优先沿用上次写在进度里的分母，所以重启不会再为了算总数去访问 `/fgk/index` 和 `/fgk/law_pagenumb`。
    - 每个编号**打开前**就把卡片文案改成「[编号 N · 已爬 M/6444] 正在打开详情页…」，并把网址行切换成**即将访问的地址**（标签显示「请求中」），不会一直停在上一页；单个页面导航上限 45 秒，超时会再用 `commit` 方式重试一次，并在日志里打「编号 N 打开较慢：xx 秒」。卡片上的「打开详情页」在 id_walk 模式下统计真实导出的 PDF 数。
    - 想换回旧的类目翻页方式：把 `crawl.crawl_mode` 改成 `category`。测试模式设了固定条数、以及"跳过分类重试"仍走类目翻页。
20. **任务异常不会再"假运行"**：中纪检/校纪检线程抛异常时，卡片会挂上红色「**异常中断**」标签并写明原因（异常类型 + 消息，如 `OSError: File name too long`），顶部同时弹出红色横幅，重启后依然保留，直到下一次成功开跑才收起。顶部「开始/暂停」图标和「终止」按钮的可用状态都跟着真实任务走；进程被强杀后重启，启动时会把残留的 `running` 复位。如果状态文件显示运行中但本进程没有对应任务（例如另一个终端在跑），终止按钮仍可点，并会提示去那个终端按 Ctrl+C。
21. **首次执行标记只在编号扫到上限时才注销**：`crawl_mode: id_walk` 时，`id_walk.ccdi.last_id` 没到 `crawl.id_walk_max` 就一直算「首次执行」，即使状态文件里 `pass_done` 是旧版本留下的 `true` 也不会提前清掉；只有编号确实扫到上限、且中纪检/校纪检都完整跑完，才切换成「日常执行」。
22. **失败编号（`failed_ids`）批量重试**：只有「页面打不开/读不到内容」「PDF 导出失败」「断点那条没落盘」才算失败；页面提示「输入有误」的编号在重试时会**从 failed_ids 移除**（它本来就不存在）。有失败编号时自动开启重试开关：以第一条失败出现的 `failed_since` 为基准，**每 30 分钟**批量重试一次，**最多 3 轮**；全部成功就关闭开关，3 轮后仍失败则在顶部红色横幅列出编号。UI 的失败编号卡片显示总数、下次重试时间，可「展开编号」「立即重试」。重试补齐了首次运行的最后一条时会自动上传全部文件，并把「首次执行」切换到「日常执行」。
23. **分类缺失的兜底**：详情页有效但 `分类：` 只有一级（如 `党内法规制度`）→ 放进 `中纪检/党内法规制度/其他/`，命名 `其他[序号] 标题.pdf`；连一级分类都没有 → 放进 `中纪检/其他/`，命名 `[序号] 标题.pdf`。子分类进度面板会多出 `党内法规制度/其他`、`国家法律法规/其他`、`其他（未归类）` 三行，总数用减法算（一级其他 = 全部总数 − 两个一级目录总数；二级其他 = 一级总数 − 各二级总数之和），量不到一级总数时显示 `—`。
24. **界面布局**：中纪检卡片下方是左右两栏——左边「中纪检 · 子分类进度」，右边上下两张等宽卡片「上次区间 / 有效编号」「失败编号」，两栏等高；运行模式里的只读「配置」改成可点击展开/收起的折叠块。
25. **附带脚本**：`count_files.py` 统计 data 目录里两个来源的 PDF 数量（`--detail` 按主分类/子分类两级展开）；`find_missing_ccdi.py` 独立核对某个分类页有没有漏爬（只读，会按标题/编号比对 `crawler_state.json`，必要时打开详情页）。
26. **版本去重、断点续联与迁库**：标题末尾的“（2017年修改）/（修订）”等修改说明会被去掉后聚合版本族；最新版本先比较有效年份，年份相同时再按标题排序。日期补录后仍无日期的文件，会从文件名（如 `（2003年修订）`、旧 `_YYYYMMDD`）兜底提取。**程序重启时就会自动执行**“扫描补登记遗留 PDF → 中/校纪检回填缺失日期 → 分别建立两来源版本索引”，不再要求先点击迁库。日期补录通过 `backfill_resume.json` 保存年份和分页断点。迁库成功后同步更新 `ragflow.dataset_id_ccdi` / `dataset_id_bit`，以及每个成功上传文件在 `documents` 和版本记录中的 `upload_dataset_id` / `uploaded_at`。

## 已知限制

- 中纪检总数是**估算**（按每页条数与总页数推算），站点改版或末页条数变化时可能与实际略有偏差。
- `upload.max_age_days` 目前不参与判断：文件满 `min_age_days` 后即会上传，失败会在后续上传任务中继续重试。
- RAGFlow 不通时爬取仍会保存本地 PDF，上传失败只体现在日志与界面提示中。
